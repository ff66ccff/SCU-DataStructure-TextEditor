## 4. 跨文档冲突：capacity 调和方案的技术判断

**我的判断：技术上自洽（能实现、不炸），但语义空转，且引入了没有守护的新不变式；更简单的是把字段从协议里删掉。**

推演依据：
- 分配策略由 C4:104 与 Q3:191 锁定为「一律先分配新数组再释放旧数组」；`analysis_core.md:121` 明确「不 realloc / 不维护 capacity」；`analysis_core.md:112,221` 与 5.5「两遍法」都要求**精确分配 newLen+1**，插入是 `len+1`。
- 因此**任何时刻都有 capacity == len + 1**，它是 len 的纯函数。
- 而 ROADMAP:110 说它是「变长替换真的换了空间」的**唯一可视证据**，`analysis_viz.md:180` 说它「暴露真实分配容量」，`analysis_viz.md:357` 断言步骤 8「capacity 增大」。这些说法不成立：capacity 增大只是因为 len 增大，它不能证明发生了「重新分配」；真正的证据是 `content_rev` 递增（`analysis_viz.md:196,212`）与 `content_changed` 事件。
- 代价侧：C8:108 的不变式只有 I1–I4，**没有一条约束「已分配字节数」**；§5 A1–A10 也不校验它 → 这个字段可以在创建/替换路径上悄悄漂移而无人发现，属于"新增状态但无守护"的典型。

**建议改法（二选一，推荐 a）**：
- **(a) 删字段**：表格 9:207 只要求「内容更新 + 保留同一标识 + 区分空文档/空行」，`content_rev` 已完全承担；删掉 `node.capacity`（`analysis_viz.md:195` 必填、:180、:357 同步改），跨文档冲突消失，core 的「不维护 capacity」保持不变，零成本。
- **(b) 保留但不落存储**：协议字段保留，定义为派生的 `len+1`，结点上不存 size_t；§4.1 增不变式 I5 `allocated == len + 1`，并在 A 断言里可校验。

**F8【建议】C5 与 §4.3 的接缝未定义。** C5:105 要求删除时先「复制（供 trace）」；§4.3:140 要求「关闭 trace 时编辑逻辑零分支差异」。两条同时满足只有一种写法：**复制发生在 trace 观察者内部**，核心只在固定点调用「可能为空的观察者」（空实现即 no-op），核心代码无分支。若把复制无条件写进核心删除路径，则 trace-off 时白白付出一次拷贝与一次分配（虽不违反"零分支"，但违背"trace 零影响"的本意）。**建议**在 §4.3 明确这个接缝。

**附注（F19，可选）**：`analysis_viz.md:115` 要求协议支持 `sentinel:none|head|head+tail`（因为指导书:17 把哨兵选择留给小组、且"每人说明自己的选择"）；ROADMAP C1:101 锁定双哨兵。若本 roadmap 只服务单一实现者，锁定无问题；但若组内三人各自提交，建议 §4.1 加一句「本路线为本人选择，不要求全组一致」。请 Lead 确认口径。

## 6. 命令集风险

**先给结论：命令字符与指导书无冲突。** 指导书:150 明确「协助与退出自行定义命令字符」，只强制 `h/H`；ROADMAP §4.2:116 满足。`h/H p n u f l g i d r / s c e w q x` 这套字符里，`h/H n u f l g i d r s c e w q` 与指导书表格 2 无任何字面冲突，扩展字符 `x` 也满足指导书:24「扩展功能使用单独命令」的纪律（§4.2:133）。

**真问题（真·设计缺陷，非风格）：**

**F12【建议】两个命令的"非法输入"分支没有定义，而指导书正好要求了。**
- 指导书:31 明写「**查找串**和待替换串不能为空」。A5:152 只定义了「空文档返回未找到」，**没有定义 `/` 后为空串时的行为**（提示？当普通查找？）；§4.2:124 也没写。
- `s` 只有合法形式 `s /old/new/`（:125, Q6:194），**畸形形式全部未定义**：缺结尾 `/`（`s /a`）、多余分隔符（`s /a/b/c`）、`old` 为空（`s //x/`）、分隔符本身要作为内容（old/new 含 `/`，Q6:194 一句「不支持转义」带过，等于永远无法替换含 `/` 的串）。
- **建议**：§4.2 补一张文法与错误处理表（缺 `/` → 提示非法命令；多于两个分隔符 → 提示非法；`old` 空 → 提示；`new` 空合法），并在 §6 补 3 条命令行级用例。

**F13【建议】`i`/`r` 的「行尾余下内容」规则只在 analysis_core 里，roadmap 未写。** `analysis_core.md:308` 定义「保留内部空格，**去掉分隔用的一个前导空格**」；§4.2:121,123 只写 `i 文本`/`r 文本`。后果：想插入以空格开头的行必须敲两个空格，规则不写进冻结契约，则（a）帮助文本 `h/H` 没法说明，（b）A 断言与 T 用例也无法判定。**建议**把该解析约定提到 §4.2，并要求 `h/H` 帮助中给出示例。

**F14【建议】未保存确认的交互语法未定义，且只测了「取消」。** T11:175 = 「未保存时**取消**重新读入或退出」；A9:156「未保存取消则完全保留」。**「确认后真的重新读入/退出」这条路径没有测试**，且确认输入本身（`y/n`？回车？）§4.2:127,129 未定义。**建议**：定义 `y/n` 并补一条用例。

**F15【建议】`x` 命令的产出语义未定义。** §4.2:130 只写「导出当前真实链表快照」，**没有输出路径、是否追加/覆盖、与 `--trace` 是否写同一文件**；`analysis_viz.md:662` 的拍板项里运行期命令还叫 `t`，与 roadmap 的 `x` 命名漂移。**建议**：§4.2 写明默认路径与覆盖策略，并统一命名为 `x`。

**风格偏好（明确不算真问题，不建议为此改契约）：**
- `l`（末行）在等宽字体下与数字 `1` 形近、且与 `p`（显示）语义容易记混——但指导书不管字符选择，改与不改都不影响评分。
